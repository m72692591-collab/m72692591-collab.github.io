## База для размещения
- infra/runtime/compose.yaml: три контейнера Nginx, PHP-FPM и MySQL. Только 127.0.0.1:8082 для сайта; PHP/MySQL не имеют публичных портов, база на named volume.
- tools/package_maestro.py: статические публичные файлы создаются в новом каталоге dist/maestro с HTTPS-origin реального домена и API /api/leads. Не создавать пакет поверх уже существующего dist — сборщик намеренно запрещает перезапись.
- infra/runtime/README.md: действующие команды, требования к четырём server-side secret files и тесты запретов. Внимательно прочитать до действий.
- frontend-консультант и сервер приёма заявок НЕ равны действующему Amvera-боту; соединение и реальное уведомление владельца — отдельная обязательная приёмка.

## Затвор до запуска ресурса
1. Владелец получил письменные условия Яндекса: конкретный грант (AI Studio не обязательно покрывает VM), срок, доступная зона и квоты. В октябре 2026 действуют восстановительные ограничения после инцидента; проверить выбранную зону.
2. Есть подтверждённый аккаунт, реальный тестовый HTTPS-адрес, отдельный подтверждённый финансовый лимит и смета после гранта. Не исходить из акции бесплатных сервисов без проверки права аккаунта.
3. Созданы безопасно четыре независимых случайных секретных файла ВНЕ Git с ограниченными правами: db_password, db_root_password, admin_token, ip_pepper. Не использовать секрета CI.
4. Выбран официальный Linux/Docker хост, закрытый внешним сетевым экраном: MySQL и FPM снаружи недоступны, административный доступ ограничен; веб — только через TLS шлюз.
5. Проверена фактическая IP-топология HTTPS reverse proxy: ограничение запросов нельзя полагаться на неизвестный/поддельный X-Forwarded-For. Проверить два разных клиента и подделку заголовка.
6. Предыдущий рабочий адрес, БД, платежи, боты и DNS не меняются до успешной приёмки.

## Подготовка релиза — только после выбора HTTPS-origin
Из проверенной чистой копии именно выбранного SHA:
1. Зафиксировать git SHA, выполнить unit/smoke/сквозной тест на СИНТЕТИЧЕСКОЙ заявке.
2. Собрать пакет командой python3 tools/package_maestro.py --origin <approved https origin>. Убедиться, что пакет не содержит .env, токенов, SQL/PHP.
3. Проверить docker compose -f infra/runtime/compose.yaml config --quiet с установленными MAESTRO_ORIGIN и MAESTRO_SECRET_DIR; затем после разрешения и установки зависимостей собрать и запустить три контейнера.
4. Проверить HTTPS: /healthz, /maestro/, /api/leads; внутренние пути /maestro/server, .env и любые файлы PHP/SQL недоступны.
5. Синтетическая заявка: согласие → один номер → повтор не даёт дубликат → другая полезная нагрузка с тем же UUID отвергается. Владелец реально получает отдельное уведомление; запись только в БД не является доставкой.
6. Проверить данные после перезапуска контейнеров, независимую зашифрованную резервную копию и ВОССТАНОВЛЕНИЕ В ОТДЕЛЬНУЮ ТЕСТОВУЮ БД. Не выполнять docker compose down -v к рабочим томам. Зафиксировать конкретные версии образов/digests.
7. Проверить оператора персональных данных, согласие, сроки удаления, отсутствие конфиденциальных полей в публичных/рекламных логах, лимиты запросов и бюджетные пороги.
8. Только после отдельного согласия DNS и проверенного отката переключать основной домен; прежний источник оставить доступным.

Если Яндекс пока не даёт квоту, те же Dockerfile/Compose можно использовать на совместимом Linux VPS, без пересборки бизнес-логики. Контур Анимы от базы и бота МАЭСТРО изолирован.

## Отдельно о новом 3D-режиме
Перенос классического проверенного сайта не должен блокироваться разработкой MAESTRO NEXT 3D. Перед публикацией последующего 3D-выпуска нужно дополнить allowlist tools/package_maestro.py форматами реально используемых 3D-ресурсов (GLB/glTF, текстуры, шейдеры/wasm при необходимости), повторно проверить, что они публичные и не включают исходники или секреты.
